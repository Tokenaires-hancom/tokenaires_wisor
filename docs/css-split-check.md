# globals.css 분할 — 눈으로 확인할 것

`app/globals.css` 5,316줄을 12개 파일로 나눴습니다. **규칙은 하나도 바꾸지 않았고**
파일만 잘랐습니다. 그래도 CSS는 테스트도 빌드도 레이아웃 파손을 잡지 못하므로,
아래를 사람이 봐야 합니다.

기계가 대신 봐 준 것 둘은 아래 "기계가 확인한 것"에 적었습니다. 그 둘이 통과했다는
말은 **규칙의 내용과 순서가 그대로**라는 뜻이지, 화면이 멀쩡하다는 증명은 아닙니다.

## 어떻게 나눴나

## 기계가 확인한 것

1. **원본과 내용·순서가 같다** — 12개 파일을 위 표 순서대로 이어붙인 것이 분할 전
   `globals.css`와 바이트 단위로 동일합니다(`cmp`, 112,343 bytes). 규칙이 하나도
   빠지거나 자리를 바꾸지 않았다는 뜻입니다.

2. **브라우저가 받는 CSS도 바이트 단위로 같다** — 이게 실제로 중요한 검증입니다.
   빌드하면 Next가 12개를 두 청크로 묶는데, HTML의 `<link>` 순서대로 이어붙이면
   분할 전의 단일 청크와 **완전히 동일합니다**.

   ```
   분할 전  d496c594….css                        78,945 bytes
   분할 후  8e0e5823….css + 1ec7a8b6….css        67,686 + 11,259 = 78,945 bytes  → cmp 동일
   ```

   `home-v5.css`와 `master-tabs.css`의 청크도 분할 전과 바이트가 같습니다.

   **셀렉터 등장 순서만 비교하면 틀립니다.** 산출 파일을 파일명 순서로 이어붙이면
   해시 순서라 실제 로드 순서와 무관합니다. 처음에 그렇게 재서 "순서가 바뀌었다"는
   잘못된 결과가 나왔습니다. 반드시 HTML의 `<link>` 순서로 이어붙여야 합니다.

3. **깜빡임은 생기지 않는다** — 브라우저가 받는 CSS 파일이 1개에서 2개로 나뉘었지만,
   빌드된 HTML에서 두 `<link rel="stylesheet">`가 **둘 다 `</head>` 앞**에 있습니다.
   렌더 블로킹이라 둘 다 받기 전에는 그리지 않습니다. 스타일이 빠진 화면이 잠깐
   보이는 일은 없습니다.

이 셋으로도 **못 잡는 것**이 남습니다. 규칙과 순서가 같아도, 화면이 실제로 의도대로
보이는지는 기계가 판정할 수 없습니다. 위 11개 목록이 필요한 이유입니다.

## 이 변경이 고치지 못한 것

전체 점검이 지적한 것은 "전역이라 한 화면 고치려 열면 열 개가 사정권에 들어온다"였습니다.
**분할은 그 문제를 없애지 못합니다.** 12개 다 여전히 `layout.tsx`가 읽는 전역이고,
`stock.css`를 고치면 여전히 모든 화면에 닿습니다.

나아진 것은 **어느 파일을 열지 알 수 있다**는 것뿐입니다. 홈을 고치려고 5,316줄을
열지 않고 288줄을 엽니다.

전역 범위 자체를 없애려면 규칙을 화면별 스코프로 옮겨야 하는데, 그러면 CSS가 실리는
시점이 바뀌어 위험이 훨씬 큽니다. 이번에는 하지 않았습니다.
