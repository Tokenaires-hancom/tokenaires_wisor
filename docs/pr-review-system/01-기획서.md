# 클린 코드 검수 시스템 — 기획서

## 배경 (기획 의도)

Wisor는 4명 모두 비개발자인 팀이 각자 Claude Code로 코드를 만드는 프로젝트다. 여기서 "클린 코드"라는 말 자체가 다시 정의되어야 한다 — 전통적인 클린 코드는 "사람이 읽고 판단한다"는 전제 위에 서 있는데, 이 팀은 그 전제가 성립하지 않는다. 코드를 읽고 "이게 좋은 코드인지" 판단할 사람이 없고, 애초에 코드 대부분을 사람이 아니라 AI가 짠다.

지금까지는 PR 자동검사·리뷰 시스템(2026-08-11)으로 규칙 위반과 일반 품질을 점검해왔지만, 병합을 막는 장치가 없어 사람이 코멘트를 놓치면 그대로 넘어갔다. AI가 코드 대부분을 작성하는 환경에서 필요한 건 "코드를 읽고 잘 짰는지 판단하는 시스템"이 아니라, **"AI가 짜준 코드가 이 프로젝트에 맞게 효율적이고 낭비 없이, 문제없이 돌아가는지 검수하는 시스템**"이다.

이 기획서는 두 가지를 다룬다.

1. AI 시대, 비개발자 팀에게 맞는 "클린 코드"를 다시 정의한다.
2. 그 정의를 Wisor 프로젝트에 실제로 적용하는 방법을 정리한다.

## 클린 코드란 무엇인가 — AI 시대의 재정의

전통적인 클린 코드(로버트 마틴류)는 "사람이 읽기 쉬운 코드"를 최우선 미덕으로 삼는다. 이 팀에는 두 가지 이유로 이 전제가 안 맞는다.

- **읽을 사람이 없다** — 4명 다 비개발자라, 코드를 읽고 품질을 판단할 수 없다.
- **짜는 주체가 AI다** — "사람이 읽기 좋은가"보다 "AI가 다시 이 코드를 정확히 이해하고 고칠 수 있는가"가 더 중요하다.

그래서 "읽기 좋음"이 아니라 **"검증 가능함"**을 축으로 다섯 가지로 재정의한다.

1. **읽지 않고도 검증 가능해야 한다** — 통과/실패가 명확한 자동 테스트나 눈으로 확인 가능한 동작이 "코드가 맞다"는 증거를 대신한다.
2. **파급 범위(blast radius) 최소화** — 한 기능을 고치라고 AI에 시켰을 때 다른 곳이 깨지지 않도록 모듈을 작게, 서로 독립적으로 쪼갠다. 비개발자는 diff를 봐도 부작용을 못 알아챈다.
3. **중복 제로에 가깝게** — 같은 로직이 여러 곳에 있으면 AI가 한 곳만 고치고 나머지를 놓쳐서 눈에 안 보이는 불일치가 생긴다. 전통적 DRY보다 훨씬 엄격하게 지킨다.
4. **평범하고 뻔한 패턴 우선** — 똑똑한 트릭·추상화는 AI도 잘못 이해하고 재생성할 확률을 높인다. 예측 가능한 관용구가 "안전한" 코드다.
5. **의도는 자연어로 별도 기록** — 코드 내 주석보다 커밋 메시지·PR 본문에 "왜 이렇게 했는지"를 남겨야, 다음에 AI에게 다시 시킬 때 맥락을 넣어줄 수 있다.

**이 다섯 가지는 검증 방식이 다르다.**

- 1·3번(테스트 통과 여부, 문자 그대로의 중복)은 **기계적으로 참·거짓을 증명할 수 있다** → 강제(하드블록)한다.
- 2·4·5번(파급범위 적정성, 패턴의 관용성, 의미상 중복, 메시지 충실도)은 **판단이 필요하다** → 확신도가 높은 LLM 의견이라도 틀릴 수 있고, 이 팀은 그 판단을 반박할 근거가 없다. 항상 "경고 + 사람 승인 후 수정"으로만 다루고 강제로 막지 않는다.

## 이 프로젝트에서 어떻게 적용하는가

기존 PR 자동검사·리뷰 시스템(2026-08-11)의 인프라를 최대한 재사용한다 — 이미 있는 것 위에, 정말 없는 부분만 새로 얹는다.

| 원칙 | Wisor에서의 적용 | 검증 방식 |
|---|---|---|
| ① 검증 가능성 | 커밋마다 로컬에서 변경 영역 테스트 실행. push 시 `pr-review.yml`이 `data-pipeline`·`web` 전체 테스트·빌드·타입체크·번들누출·경계 검사 수행 | 하드블록 (결정론적) |
| ③ 중복 제로 | 신규 스크립트로 문자 그대로의 중복 탐지 (로컬 커밋마다 + `pr-review.yml`에서 PR 전체 diff 기준으로 재확인) | 하드블록 (결정론적) |
| ② 파급범위 | `/code-review`가 CLAUDE.md에 명시된 원칙을 push 전 감사 | 경고 → 승인 시 수정 |
| ④ 평범한 패턴 | `/simplify`가 push 전 재사용·단순화·효율 점검 | 경고 → 승인 시 수정 |
| ⑤ 의도 기록 | 기존 커밋/PR 형식 규칙(`type: 설명`, PR 템플릿 3섹션) 유지, `pr_format_check.py`가 확인 | 소프트 게이트 (기존 유지) |

**로컬 하드블록을 우회(`git commit --no-verify` 등)해도, `pr-review.yml`을 branch protection 필수 상태 검사로 등록해 서버에서 최종적으로 막는다.** 로컬 게이트는 "빠른 1차 필터", 서버는 "우회 불가능한 최종 방어선"으로 역할을 나눈다.

Wisor 도메인 고유 규칙(매수·매도 권유 금지, 금지 문구, 화면↔재무데이터 경계 등)은 클린 코드 원칙과 별개다. "코드가 깨끗한가"가 아니라 "이 제품이 지켜야 할 약속을 지켰는가"의 문제다. 원래는 `claude-rules-review.yml`이 전담했지만, ②(`/code-review`)가 CLAUDE.md 전체를 감사 근거로 삼으므로 이 판단도 함께 흡수하기로 하고 `claude-rules-review.yml`·`claude-quality-review.yml` **둘 다 폐기한다.** ②는 로컬 세션에서만 도는 한계가 있어(터미널 push 등에는 안 걸림) 서버가 항상 도는 것보다 약한 보장이지만, 저장소의 과거 커밋으로도 "Claude Code를 거쳤는지"를 사후 확인할 방법이 원래 없었다는 점(트레일러 관행 자체가 없음)을 근거로 이 리스크를 받아들이기로 했다.

## 목표

1. AI가 만든 코드가 위 5원칙을 지켰는지 커밋·push 시점에 자동으로 검수한다.
2. 기계적으로 증명 가능한 위반(테스트 실패, 문자 그대로의 중복)은 하드블록으로 막는다.
3. 판단이 필요한 위반(파급범위, 패턴, 의미상 중복)은 경고하고, 사람이 승인해야만 고쳐지게 한다.
4. push 전에 미리 걸러서, PR을 올린 뒤에야 문제를 발견하는 왕복을 줄인다.
5. 로컬 게이트를 우회해도 서버(branch protection)에서 최종적으로 막는다.

## 목표가 아닌 것

- **4명이 "좋은 코드를 알아보는 눈"을 기르는 걸 목적으로 최적화하는 것.** `claude-quality-review.yml`은 "가장 배우기 좋은 2~3개만 고르고 개념을 가르치는 문체로 설명"하도록 학습을 목적으로 설계돼 있었다 — 이 목적 자체를 폐기한다. 대신 ②(push 전 `/code-review`+`/simplify`)의 결과가 PR에 코멘트로 남긴 하지만, 이건 "검수가 실제로 일어났다"는 팀 신뢰·가시성을 위한 기록이지 배우기 좋은 순으로 고르거나 가르치는 문체로 쓰지 않는다. 결과적으로 설명이 붙은 코멘트를 보며 부수적으로 배우는 것까지 막지는 않지만, 그걸 위해 캡을 두거나 문체를 조정하지는 않는다.
- **판단이 필요한 원칙(파급범위·패턴·의미상 중복·메시지 충실도)을 하드블록하는 것.** 확신도가 높아도 이 팀은 LLM 판단을 반박할 수 없으므로, 항상 사람이 최종 승인한다.
- **새 외부 의존성을 추가하는 것.** git 내장 기능(`core.hooksPath`)과 Python 표준 라이브러리만 쓴다.
- **개별 커밋 메시지 형식을 하드블록하는 것.** `pr_format_check.py`가 PR 제목·본문 형식을 이미 검사하고 있어 중복으로 판단해 제외했다.

## 성공 기준

- 테스트가 실패한 상태이거나 명백히 복붙된 코드가 커밋되는 일이 사라진다.
- 파급범위·패턴 문제가 PR에서 처음 발견되는 대신, push 전 로컬에서 먼저 발견·수정되는 비율이 늘어난다.
- 로컬 하드블록을 우회해도 branch protection에서 병합이 최종적으로 막힌다.
- `.claude/`, `.githooks/`, `CLAUDE.md` 등 이 시스템 자체의 설정 파일은 게이트키퍼(naemnaem99) 승인 없이 바뀌지 않는다.
- 하드블록 오버라이드가 발생하면 그 사실이 PR에 흔적으로 남는다.
