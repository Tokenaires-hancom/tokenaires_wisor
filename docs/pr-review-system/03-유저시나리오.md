# 클린 코드 검수 시스템 — 유저 시나리오

작성일 2026-08-18 (2026-08-13 작성 원본을 대체)
관련 기획: [`01-기획서.md`](./01-기획서.md) · 관련 다이어그램: [`02-시스템설계도.md`](./02-시스템설계도.md)

유저는 PR을 올리는 4인 팀원(`naemnaem99`, `rainbow0291`, `chrusterd`, `limsojang-gif`) 중 한 명이다. 네 시나리오는 각각 ①(로컬 하드블록) · ②(push 전 검수, 클린코드+도메인 규칙 통합) · 서버 최종 방어선(오버라이드+게이트키퍼) · ②의 도메인 규칙 판단(옛 `claude-rules-review.yml` 역할 흡수)이 실제로 작동하는 경우를 다룬다.

---

## 시나리오 A — 로컬 하드블록이 테스트 실패를 막고 자동으로 고친다

**등장인물**: `naemnaem99` (스타일 점수 계산 로직 수정 중)

naemnaem99가 새 점수 기준을 추가하면서, 기존 `metrics.py`의 함수 시그니처를 살짝 바꿨다. 화면은 로컬에서 잘 뜬다 — 커밋하기 전까지는 아무것도 이상해 보이지 않는다.

1. `git commit`을 시도한다. Claude Code로 커밋 중이라 `.claude/hooks/require-review-before-commit.sh`가 개입한다.
2. 변경 영역(`data-pipeline`)에 해당하는 테스트만 빠르게 돌린다 — `test_metrics.py`가 하나 실패한다. 시그니처 변경으로 다른 곳에서 호출하던 자리가 깨졌다.
3. 커밋이 **차단**된다. Claude가 자동으로 원인을 찾아 구현 코드를 고친다(테스트 파일 자체는 건드리지 않는다 — 테스트를 고쳐서 통과시키는 건 금지돼 있다).
4. 재검사에서 통과한다. 수정 내용은 원래 커밋에 합쳐지지 않고 `auto-fix: metrics.py 시그니처 변경에 맞춰 호출부 수정` 별도 커밋으로 분리된다.
5. 커밋이 완료된다. 이 과정 전체가 로컬에서, push하기 훨씬 전에 끝난다 — PR에는 아무 흔적도 안 남는다(정상 자동수정은 기록하지 않기로 했다).

## 시나리오 B — push 전 검수가 파급범위 문제를 미리 잡아준다

**등장인물**: `rainbow0291` (스크리너 필터 기능 추가 중)

rainbow0291이 필터 기능 하나를 추가하면서, 화면 컴포넌트·API 라우트·타입 정의·테스트 헬퍼까지 6개 파일을 고쳤다. 각 커밋은 ①(테스트·중복)을 문제없이 통과한다.

1. 작업을 마치고 `git push`를 시도한다.
2. 세션이 이번 push로 나갈 커밋 전체 diff에 `/code-review`를 돌린다. CLAUDE.md의 클린코드 원칙 섹션("파급범위 최소화")을 근거로, 타입 정의 변경이 굳이 안 건드려도 될 두 파일까지 연쇄적으로 고치게 만들었다는 걸 짚는다.
3. "이 부분은 파급범위가 커 보입니다. 타입을 좁게 나누면 나머지 4개 파일은 안 건드려도 될 것 같은데, 고칠까요?"라고 물어본다.
4. rainbow0291이 "응"이라고 답한다. Claude가 그 자리에서 타입을 나누고, 영향받는 파일 수를 6개에서 4개로 줄인다. (사람이 그 자리에서 승인했으므로 재검증 없이 바로 반영된다.)
5. `/simplify`까지 마저 돌고, 발견 사항이 더 없으면 push가 마무리되어 PR이 생성된다.
6. push 직후, 방금 로컬에서 나온 리뷰 결과가 PR에 `<!-- wisor-local-review -->` sticky 코멘트로 남는다 — "파급범위 지적 1건, 반영함"이라고 기록된다. 리뷰를 다시 돌린 게 아니라 로컬 결과를 재활용한 것이라 추가 비용이 없다.

## 시나리오 C — 오버라이드하면 게이트키퍼 승인 없이는 병합이 안 된다

**등장인물**: `limsojang-gif`

limsojang-gif가 급하게 처리해야 하는 수정을 하다가, ①에서 문자 그대로의 중복이 걸린다. 자동 수정을 2회 시도했지만 실패한다 — 두 코드가 미묘하게 다른 맥락이라 자동으로 함수를 뽑아내기 애매한 경우였다.

1. 2회 실패 후 커밋이 계속 차단된 상태다. limsojang-gif는 사유("두 곳 다 확인했고, 지금은 의도적으로 남겨둠 — 다음 PR에서 정리 예정")를 남기고 오버라이드로 강행한다.
2. 커밋은 완료되고, 이후 push할 때 이 사실이 PR에 흔적으로 남는다 — "⚠️ 하드블록 오버라이드됨: 중복 코드, 사유: ..." 형태로 기록된다.
3. push는 정상적으로 진행되고 `pr-review.yml`도 문제없이 통과한다. 하지만 **오버라이드 흔적이 있으므로**, `pr-review.yml`의 마지막 스텝이 이를 감지해 chrusterd를 리뷰어로 지정한다.
4. 다른 팀원 3명 중 누군가 승인해도, **chrusterd가 별도로 승인하기 전까지는 병합 버튼이 비활성화된다** — branch protection이 코드오너 승인을 요구하기 때문이다.
5. chrusterd가 흔적 코멘트와 사유를 확인하고, 실제로 다음 PR에서 정리하기로 하고 승인한다. 그제야 병합이 가능해진다.

오버라이드 자체를 막는 건 아니다 — 다만 그 결정이 조용히 묻히지 않고 **반드시 게이트키퍼의 눈을 거치게** 만든다.

## 시나리오 D — push 전 검수가 도메인 규칙 위반도 잡는다 (옛 규칙 리뷰 역할 흡수)

**등장인물**: `chrusterd` (스크리너 화면 문구 작업 중)

2026-08-11 설계에서는 이 역할을 `claude-rules-review.yml`이 PR 오픈 후 별도로 맡았다. 이번 설계에서 그 레이어는 폐기됐고, ②가 같은 판단을 push 전에 대신한다.

chrusterd가 요약 문구를 "8개 기준 중 6개를 충족해 지금 사야 할 만합니다"라고 썼다. ①(테스트·중복)은 이 문제를 안 본다.

1. `git push`를 시도하면 ②(`/code-review`)가 루트 `CLAUDE.md`의 "사용자에게 보이는 문장 규칙" 표를 감사 근거로 읽는다.
2. "지금 사야 합니다" 류 금지 문구가 그대로 쓰인 걸 발견하고, CLAUDE.md의 해당 행("지금 사야 합니다 → 8개 기준 중 6개에 부합합니다")을 그대로 인용하며 "고칠까요?"라고 물어본다.
3. chrusterd가 승인하면 그 자리에서 문구가 바뀌고, push가 진행된다.
4. push 직후 PR에 `<!-- wisor-local-review -->` 코멘트로 "문장 규칙 위반 1건, 반영함"이 기록된다 — 예전에 `claude-rules-review.yml`이 인라인 코멘트로 남기던 것과 같은 근거(CLAUDE.md 표 인용)를 쓰지만, 이제는 push 전에, 한 번의 검수 안에서 같이 처리된다.

이 판단은 여전히 하드블록이 아니다 — chrusterd가 "아니오"라고 답했어도 push는 그대로 진행됐을 것이고, 그 경우 "발견했지만 반영 안 함"으로 기록되어 나머지 3명이 PR에서 확인할 수 있다.

## 네 시나리오의 공통점과 차이점

- **①·서버 최종 방어선은 병합/커밋을 실제로 막는다.** 이건 2026-08-11 설계와 가장 크게 달라진 점이다 — 그때는 "아무것도 강제로 막지 않는다"가 원칙이었다.
- **②(클린코드+도메인 규칙+일반 품질 통합 판단)는 병합을 막지 않는다.** 판단이 필요한 영역은 항상 "알려주고, 사람이 승인해야 반영"하는 방식을 유지한다 — 대신 ②는 로컬 세션에서만 돌기 때문에, 실행이 보장되지 않는다는 리스크를 감수하기로 했다(01-기획서.md 참고).
- **정상적인 통과·자동수정은 흔적을 남기지 않는다.** 오버라이드처럼 예외적인 경우만 PR에 기록해서, 코멘트가 쌓여 아무도 안 읽는 상황을 피한다.
- **설정 파일(`​.claude/`, `.githooks/`, `CLAUDE.md`) 자체를 고치는 PR은 항상 chrusterd 승인이 필요하다** — 시나리오 C와 별개로, 경로 기반으로 항상 걸린다.
