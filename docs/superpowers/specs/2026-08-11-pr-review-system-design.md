# PR 코드 리뷰 시스템 — 설계

작성일 2026-08-11

---

## 배경

4명 모두 비개발자이고 각자 Claude Code로 코드를 만든다. 지금까지 대부분의 변경은 PR 없이 `develop`에 직접 커밋됐다(병합 PR은 21개 커밋 중 1개뿐). `CLAUDE.md`는 커밋 전 세 영역(data-pipeline·chart-api·web)의 테스트·빌드를 사람이 직접 돌리도록 요구하고, 세 가지 핵심 원칙·경계 규칙·번지는 지점을 문서로 적어뒀지만 실행을 강제하는 장치는 없다.

이 설계는 두 가지를 함께 다룬다.

1. **PR 습관 도입** — 지금부터 직접 커밋 대신 PR을 올리고 리뷰받은 뒤 병합한다.
2. **PR마다 자동으로 두 층의 리뷰를 남기는 시스템** — 규칙으로 판단 가능한 것과 판단이 필요한 것을 나눈다.

## 목표가 아닌 것

- 병합을 강제로 막는 게이트를 만들지 않는다. 병합 여부는 사람이 정한다.
- `CLAUDE.md`의 "1번·2번·3번·4번" 역할·리뷰 담당 표는 지금 실제로 쓰이지 않는다. 이 시스템은 그 표를 근거로 특정 역할에게 리뷰를 지정하지 않는다.
- 새 외부 의존성을 추가하지 않는다(루트 `CLAUDE.md`의 "의존성 추가 금지" 원칙).

## 결정 사항

### 1. 트리거

`.github/workflows/pr-review.yml`이 `pull_request`(opened, synchronize, reopened) 이벤트에서 두 개의 독립된 잡으로 실행된다. 두 잡 모두 실패해도 워크플로 자체는 실패로 표시될 수 있지만(정상적인 CI 신호), 브랜치 보호 규칙으로 병합을 막지는 않는다. 병합 여부는 사람이 코멘트를 보고 정한다.

### 2. 자동검사 레이어 (규칙 기반, 무료)

`CLAUDE.md` "명령" 섹션에 이미 적힌 세 가지를 PR마다 전부 실행한다(문서 그대로 — 어느 영역을 고쳤든 전부 돌린다).

```
cd data-pipeline && pytest -q       # BANNED_PHRASES 검사 포함
cd services/chart-api && pytest -q  # safety.py RULES 검사 포함
cd apps/web && npm run build
```

여기에 `CLAUDE.md`에 이미 문장으로 적혀 있고 grep으로 안정적으로 판단 가능한 두 규칙을 스크립트로 추가한다. 둘 다 표준 라이브러리만 쓴다.

- **`scripts/pr_checks/boundary_check.py`** — 화면 ↔ 재무데이터 경계. diff에 포함된 `apps/web` 내 파일 중 `'use client'`가 있는 파일이 `lib/scores`(타입 파일 제외)를 import하면 실패로 보고한다.
- **`scripts/pr_checks/ripple_check.py`** — 번지는 지점 중 "차트 학습 단원을 추가·삭제하면" 항목. `apps/web/content/chartLessons.ts`의 lesson id 목록과 `services/chart-api/app/services/prompt.py`의 `LESSON_IDS`를 비교해서, PR이 둘 중 하나만 건드렸으면 경고로 보고한다(둘 다 안 건드렸거나 둘 다 건드렸으면 통과).

두 스크립트는 실패해도 워크플로를 중단시키지 않는다(`continue-on-error`) — 나머지 검사 결과도 한 번에 모아서 보여주기 위해서다. 결과는 마지막 스텝에서 하나의 PR 코멘트로 정리해서 남긴다: 각 항목의 통과/실패와, 실패했다면 무엇을 확인해야 하는지.

**범위 밖으로 남기는 것**: "차트 분석기에 종목명·티커를 넘기지 않는다"는 경계는 grep으로 안정적으로 판단하기 어려워 이번에는 자동검사에 넣지 않는다(3번 레이어에서 Claude가 판단). `lib/store.ts` 시그니처 변경이나 "기준 개수" 관련 UI 문구 등 나머지 번지는 지점도 마찬가지로 3번 레이어가 맡는다.

### 3. Claude 의미 리뷰 레이어

Claude Code의 공식 GitHub 연동을 사용한다(`claude` CLI의 `/install-github-app`으로 설정). 구독 계정(Pro/Max) 기반 OAuth 토큰을 쓰므로 API 종량 과금이 없다.

리뷰 프롬프트는 PR diff와 루트 및 하위 `CLAUDE.md`를 근거로 다음만 판단한다.

- 세 가지 핵심 원칙 위반 (매수 점수 합치기 금지 / 미래 예측 금지 / 정식 기능·베타 경계)
- "사용자에게 보이는 문장 규칙" 표 위반 (금지 문구, "현재" 대신 날짜 표기 등)
- "절대 하지 말 것" 목록 중 코드로 못 잡는 항목 (unknown을 0으로 채우기, 원본 이미지 저장, 응답 스키마에 금지 필드 추가 등)
- "화면 ↔ 차트 분석" 경계 (종목명·티커가 분석기로 넘어가는지)

**명시적으로 하지 않는 것**: `CLAUDE.md`의 역할 분담 표를 근거로 "이건 3번 담당이니 1번이 리뷰해야 합니다" 같은 코멘트를 하지 않는다. 실제 역할 분담이 없는 상태에서 그런 코멘트는 혼란만 준다.

위반이 없으면 "위반 없음"이라고 명시하고, 있으면 파일:줄 번호와 함께 무엇이 왜 위반인지 설명한다. 결과는 PR 코멘트로 남는다.

### 4. 리뷰어 자동 지정

`.github/CODEOWNERS`에 저장소 전체를 4명 공동 소유로 등록한다.

```
* @chrusterd @rainbow0291 @naemnaem99 @limsojang-gif
```

PR을 열면 작성자 본인을 제외한 나머지에게 GitHub가 자동으로 리뷰 요청을 보낸다. 역할별 담당 영역을 나누지 않고 전원을 대상으로 한다 — 지금 실제 역할 분담이 없기 때문이다.

**주의**: `limsojang-gif`는 아직 저장소 초대를 수락하지 않았다. GitHub는 쓰기 권한이 있는 사용자만 CODEOWNERS로 자동 지정할 수 있으므로, 초대가 수락되기 전까지는 이 사람에게 리뷰 요청이 자동으로 가지 않는다. 초대 수락 후 별도 조치 없이 자동으로 동작한다.

### 5. PR 템플릿

`.github/pull_request_template.md`를 추가한다. `CLAUDE.md`의 "PR에는 세 가지를 적습니다"를 그대로 칸으로 만든다.

```markdown
## 무엇을 바꿨는지

## 왜

## 어떻게 확인했는지
```

## 롤아웃 절차 (사람이 직접 해야 하는 것)

이 설계로 만들어지는 코드는 저장소에 커밋되지만, 실제로 작동하려면 다음을 사람이 손으로 해야 한다.

1. 구독 계정으로 로그인한 사람이 로컬 `claude` CLI에서 `/install-github-app`을 실행해 이 저장소에 GitHub App을 설치하고 OAuth 토큰 시크릿을 등록한다.
2. `limsojang-gif`의 저장소 초대를 수락받는다(현재 대기 중).
3. 4명이 지금부터 `develop`에 직접 푸시하지 않고 `feat/`·`fix/`·`data/` 브랜치에서 작업한 뒤 PR을 올리는 습관으로 전환한다.

## 에러 처리

- 자동검사 레이어의 개별 스텝(pytest, npm build, boundary/ripple 스크립트)이 실패해도 이후 스텝은 계속 실행되고, 마지막에 전체 결과를 모아 하나의 코멘트로 남긴다. 하나가 실패했다고 나머지 결과를 못 보는 일이 없게 한다.
- Claude 의미 리뷰 잡이 실패(예: OAuth 토큰 만료)하면 자동검사 코멘트는 별도로 이미 남아 있으므로 최소한의 신호는 유지된다.
- 두 레이어 모두 브랜치 보호 규칙에 연결하지 않는다. 실패해도 병합 버튼은 항상 눌린다.

## 테스트

- `scripts/pr_checks/boundary_check.py`, `ripple_check.py`는 각각 통과 케이스·위반 케이스 샘플 diff로 단위 테스트한다(pytest, data-pipeline과 같은 표준 라이브러리 전용 스타일).
- 워크플로 자체는 테스트용 PR을 하나 열어서 두 코멘트가 정상적으로 달리는지, 위반을 심어 넣은 커밋에서 정확히 잡히는지 눈으로 확인한다(GitHub Actions는 로컬에서 완전히 재현하기 어렵다).

## 범위 밖

- 브랜치 보호 규칙으로 병합을 강제 차단하는 것
- `CLAUDE.md`의 역할 분담 표를 실제 역할 배정으로 갱신하는 것 (이 시스템과 별개 논의)
- 종목명·티커 전달 여부의 자동(grep) 검사
