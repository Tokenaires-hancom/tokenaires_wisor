# PR 코드 리뷰 시스템 — 설계

작성일 2026-08-11

---

## 배경

4명 모두 비개발자이고 각자 Claude Code로 코드를 만든다. 지금까지 대부분의 변경은 PR 없이 `develop`에 직접 커밋됐다(병합 PR은 21개 커밋 중 1개뿐). `CLAUDE.md`는 커밋 전 세 영역(data-pipeline·chart-api·web)의 테스트·빌드를 사람이 직접 돌리도록 요구하고, 세 가지 핵심 원칙·경계 규칙·번지는 지점을 문서로 적어뒀지만 실행을 강제하는 장치는 없다.

이 설계는 두 가지를 함께 다룬다.

1. **PR 습관 도입** — 지금부터 직접 커밋 대신 PR을 올리고 리뷰받은 뒤 병합한다.
2. **PR마다 자동으로 세 층의 리뷰를 남기는 시스템** — 규칙으로 판단 가능한 것, 제품 규칙 판단이 필요한 것, 일반 코드 품질 중 배울 만한 것을 나눈다.

> **갱신 이력 (2026-08-11, 같은 날)**: 어제(2026-08-10)자 실제 커밋으로 이 설계를 검증하는 과정에서 두 가지가 추가됐다 — ① `fa9eb89` 커밋이 `npm run build`만으로는 못 잡는 타입 오류를 직접 증언해서 `tsc --noEmit`과 번들 누출 grep을 자동검사에 추가했다. ② "일반 코드 품질도 리뷰하면서 공부되게 하고 싶다"는 요청으로 세 번째 레이어(학습 코드 품질 리뷰)가 생겼다. 코멘트가 push마다 쌓이지 않도록 **sticky(갱신형) 코멘트**로 방식을 명확히 했다.

## 목표가 아닌 것

- 병합을 강제로 막는 게이트를 만들지 않는다. 병합 여부는 사람이 정한다.
- `CLAUDE.md`의 "1번·2번·3번·4번" 역할·리뷰 담당 표는 지금 실제로 쓰이지 않는다. 이 시스템은 그 표를 근거로 특정 역할에게 리뷰를 지정하지 않는다.
- 새 외부 의존성을 추가하지 않는다(루트 `CLAUDE.md`의 "의존성 추가 금지" 원칙).

## 결정 사항

### 1. 트리거

`.github/workflows/pr-review.yml`이 `pull_request`(opened, synchronize, reopened) 이벤트에서 자동검사 잡을 실행한다. Claude 기반 두 레이어(3·4번)는 별도 워크플로로 연결된다 — 롤아웃 절차 참고. 어느 레이어도 브랜치 보호 규칙에 연결하지 않으므로 실패해도 병합을 막지 않는다. 병합 여부는 사람이 코멘트를 보고 정한다.

모든 레이어는 **sticky(갱신형) 코멘트**로 남는다. 레이어마다 고유한 숨김 마커(`<!-- wisor-auto-checks -->`, `<!-- wisor-claude-rules -->`, `<!-- wisor-claude-quality -->`)로 기존 코멘트를 찾아 고쳐 쓴다 — push마다 새 코멘트가 쌓이면 "뭐가 중요한지 흐려진다"는 이 시스템의 목적 자체를 어기기 때문이다.

### 2. 자동검사 레이어 (규칙 기반, 무료)

`CLAUDE.md` "명령" 섹션에 이미 적힌 세 가지를 PR마다 전부 실행한다(문서 그대로 — 어느 영역을 고쳤든 전부 돌린다).

```
cd data-pipeline && pytest -q       # BANNED_PHRASES 검사 포함
cd services/chart-api && pytest -q  # safety.py RULES 검사 포함
cd apps/web && npm run build
```

여기에 두 가지를 추가로 자동화한다.

- **`apps/web/CLAUDE.md`에 이미 적힌 확인 명령** — `grep -rl "evEbitMedian5y" .next/static/`가 비어야 한다. 빌드 후 자동으로 실행한다.
- **`npx tsc --noEmit`** — `npm run build`는 앱 빌드 그래프 밖의 `*.test.ts` 파일 타입 오류를 못 잡는다. **2026-08-10 `fa9eb89` 커밋 메시지가 이걸 직접 증언한다**: "steps.test.ts가 Step 유니온에서 좁히지 않고 .index를 바로 읽어 타입 오류였다. npm run build는 이 파일이 앱 빌드 그래프 밖이라 잡지 못했고 ... tsc --noEmit으로만 드러난다." 실제로 그날 이 오류가 났었다가 사람이 나중에 찾아 고쳤다.

그리고 `CLAUDE.md`에 이미 문장으로 적혀 있고 grep으로 안정적으로 판단 가능한 두 규칙을 스크립트로 추가한다. 둘 다 표준 라이브러리만 쓴다.

- **`scripts/pr_checks/boundary_check.py`** — 화면 ↔ 재무데이터 경계. diff가 아니라 `apps/web` 전체를 매번 스캔해서, `'use client'`가 있는 파일이 `lib/scores`(타입 파일 제외)를 import하면 실패로 보고한다. 전체 스캔이 diff 스코프보다 견고하다 — `'use client'` 지시어 자체를 안 건드리고 import만 바꾸는 경우도 잡는다.
- **`scripts/pr_checks/ripple_check.py`** — 번지는 지점 중 "차트 학습 단원을 추가·삭제하면" 항목. `services/chart-api/app/services/prompt.py`의 `LESSON_IDS`, `apps/web/content/chartLessons.ts`의 `CHART_LESSONS[].id`, **`apps/web/content/chartLessons.test.ts`의 `EXPECTED_IDS`까지 세 곳을 비교한다.** 세 번째 값은 원래 사람이 손으로 맞춘 별도 하드코딩이라 자동 교차검증이 전혀 없었다 — 이번에 처음 생기는 안전망이다. 셋 중 하나라도 다르면 무엇이 다른지 정확히 보고한다.

모든 검사 스텝은 실패해도 워크플로를 중단시키지 않는다(`continue-on-error`) — 나머지 검사 결과도 한 번에 모아서 보여주기 위해서다. 결과는 마지막 스텝에서 하나의 sticky PR 코멘트로 정리해서 남긴다: 각 항목의 통과/실패와, 실패했다면 무엇을 확인해야 하는지.

**범위 밖으로 남기는 것**: "차트 분석기에 종목명·티커를 넘기지 않는다"는 경계는 grep으로 안정적으로 판단하기 어려워 이번에는 자동검사에 넣지 않는다(3번 레이어에서 Claude가 판단). `lib/store.ts` 시그니처 변경이나 "기준 개수" 관련 UI 문구 등 나머지 번지는 지점도 마찬가지로 3번 레이어가 맡는다.

### 3. Claude 의미 리뷰 레이어

Claude Code의 공식 GitHub 연동을 사용한다(`claude` CLI의 `/install-github-app`으로 설정). 구독 계정(Pro/Max) 기반 OAuth 토큰을 쓴다.

**비용에 대한 정확한 상태**: 구독 인증은 별도 API 종량 과금 없이 구독 사용량 한도를 함께 쓴다 — 단, **자동/비멘션 트리거(PR 이벤트로 자동 실행)가 구독 인증에서도 지원되는지는 아직 검증하지 않았다.** 안 되면 API 키를 발급해서 전환하고, 이 경우 사용한 만큼 과금된다. 이 부분은 실제로 `/install-github-app`을 실행해봐야 확정된다.

리뷰 프롬프트(`.github/claude/rules-review-prompt.md`)는 PR diff와 루트 및 하위 `CLAUDE.md`를 근거로 다음만 판단한다.

- 세 가지 핵심 원칙 위반 (매수 점수 합치기 금지 / 미래 예측 금지 / 정식 기능·베타 경계)
- "사용자에게 보이는 문장 규칙" 표 위반 (금지 문구, "현재" 대신 날짜 표기 등)
- "절대 하지 말 것" 목록 중 코드로 못 잡는 항목 (unknown을 0으로 채우기, 원본 이미지 저장, 응답 스키마에 금지 필드 추가 등)
- "화면 ↔ 차트 분석" 경계 (종목명·티커가 분석기로 넘어가는지)

**명시적으로 하지 않는 것**: `CLAUDE.md`의 역할 분담 표를 근거로 "이건 3번 담당이니 1번이 리뷰해야 합니다" 같은 코멘트를 하지 않는다. 실제 역할 분담이 없는 상태에서 그런 코멘트는 혼란만 준다. 일반적인 코드 품질(버그·효율·변수명)도 다루지 않는다 — 4번 레이어가 따로 맡는다.

위반이 없으면 "위반 없음"이라고 명시하고, 있으면 파일:줄 번호와 함께 무엇이 왜 위반인지 설명한다. 결과는 `<!-- wisor-claude-rules -->` 마커의 sticky PR 코멘트로 남는다.

### 4. 학습 코드 품질 리뷰 레이어

같은 `/install-github-app` 연동을 쓰지만, 완전히 별도 코멘트(`<!-- wisor-claude-quality -->` 마커)로 남긴다. `CLAUDE.md` 규칙과는 무관하게, 일반적인 코드 품질(버그·비효율·이름 짓기)을 다룬다.

이 저장소를 만드는 4명이 전부 비개발자라서, 지적하는 것보다 **왜 문제인지 개념을 배우게 하는 것**이 목적이다. 프롬프트는 `.github/claude/quality-review-prompt.md`에 있다.

- **캡**: 발견되는 모든 문제를 나열하지 않는다. 가장 배우기 좋은(다른 곳에도 적용되는 일반적인 개념일수록 좋은) **2~3개만** 고른다. 사용자가 "지적이 너무 많으면 4명이 다 안 읽는다"고 판단했다.
- **형식**: 이 제품 자체의 문체를 그대로 가져온다 — 루트 `CLAUDE.md`의 "골든크로스" 예시처럼 관찰을 먼저 서술하고 개념 이름은 그다음에 붙인다(무엇이 보이는지 → 개념 이름 → 왜 문제인지 → 어떻게 고치면 좋은지).
- 병합을 막지 않는 참고용임을 코멘트에 매번 명시한다.

### 5. 리뷰어 자동 지정

`.github/CODEOWNERS`에 저장소 전체를 4명 공동 소유로 등록한다.

```
* @chrusterd @rainbow0291 @naemnaem99 @limsojang-gif
```

PR을 열면 작성자 본인을 제외한 나머지에게 GitHub가 자동으로 리뷰 요청을 보낸다. 역할별 담당 영역을 나누지 않고 전원을 대상으로 한다 — 지금 실제 역할 분담이 없기 때문이다.

**주의**: `limsojang-gif`는 아직 저장소 초대를 수락하지 않았다. GitHub는 쓰기 권한이 있는 사용자만 CODEOWNERS로 자동 지정할 수 있으므로, 초대가 수락되기 전까지는 이 사람에게 리뷰 요청이 자동으로 가지 않는다. 초대 수락 후 별도 조치 없이 자동으로 동작한다.

### 6. PR 템플릿

`.github/pull_request_template.md`를 추가한다. `CLAUDE.md`의 "PR에는 세 가지를 적습니다"를 그대로 칸으로 만든다.

```markdown
## 무엇을 바꿨는지

## 왜

## 어떻게 확인했는지
```

## 롤아웃 절차 (3단계)

이 설계로 만들어지는 코드는 저장소에 커밋되지만, 세 층이 한 번에 다 작동하지는 않는다 — **자동검사 레이어는 오늘 바로 동작하고, 두 Claude 레이어는 사람이 한 단계를 거친 뒤에 연결된다.** 이 순서를 명확히 해두는 이유는, 안 그러면 "PR 열었는데 코멘트가 하나(자동검사)만 달리고 나머지 둘은 왜 없지"가 마치 고장처럼 보이기 때문이다.

**1단계 (즉시)** — `pr-review.yml`이 배포되면 자동검사 코멘트(`<!-- wisor-auto-checks -->`)가 PR마다 달린다. 사람이 할 일 없음.

**2단계** — 구독 계정으로 로그인한 사람이 로컬 `claude` CLI에서 `/install-github-app`을 실행해 이 저장소에 GitHub App을 설치하고 OAuth 토큰 시크릿을 등록한다. `limsojang-gif`의 저장소 초대도 이때 수락받는다(현재 대기 중).

**3단계** — `/install-github-app`이 생성한 워크플로에 `.github/claude/rules-review-prompt.md`와 `.github/claude/quality-review-prompt.md`를 각각 참조하는 잡(또는 스텝) 두 개를 연결한다. 이후 PR마다 세 코멘트가 모두 달린다.

**병행**: 4명이 지금부터 `develop`에 직접 푸시하지 않고 `feat/`·`fix/`·`data/` 브랜치에서 작업한 뒤 PR을 올리는 습관으로 전환한다. 이건 도구가 아니라 팀 습관 문제라 1~3단계와 별개로 바로 시작할 수 있다.

## 에러 처리

- 자동검사 레이어의 개별 스텝(pytest, npm build, tsc, grep, boundary/ripple 스크립트)이 실패해도 이후 스텝은 계속 실행되고(`continue-on-error`), 마지막에 전체 결과를 모아 하나의 sticky 코멘트로 남긴다. 하나가 실패했다고 나머지 결과를 못 보는 일이 없게 한다.
- Claude 레이어(3·4번)가 실패(예: OAuth 토큰 만료)해도 자동검사 코멘트는 별도 워크플로에서 이미 남으므로 최소한의 신호는 유지된다.
- 세 레이어 모두 브랜치 보호 규칙에 연결하지 않는다. 실패해도 병합 버튼은 항상 눌린다.
- sticky 코멘트 upsert 스텝이 GitHub 토큰 권한 부족으로 실패하지 않도록 워크플로에 `permissions: pull-requests: write`를 명시한다(기본 토큰 권한이 read-only일 수 있음).

## 테스트

- `scripts/pr_checks/boundary_check.py`, `ripple_check.py`는 각각 통과 케이스·위반 케이스 fixture로 단위 테스트한다(pytest, data-pipeline과 같은 표준 라이브러리 전용 스타일). 실제 저장소 상태로도 클린 통과하는지 확인하는 통합 테스트를 하나씩 포함한다.
- 워크플로 자체는 결함 3종(경계 위반·id 불일치·좁히지 않은 타입 접근)을 심은 테스트 PR로 확인한다 — 세 가지가 정확히 잡히는지, 커밋을 여러 번 푸시해도 코멘트가 하나로 갱신되는지(새로 쌓이지 않는지)를 본다(GitHub Actions는 로컬에서 완전히 재현하기 어렵다).

## 범위 밖

- 브랜치 보호 규칙으로 병합을 강제 차단하는 것
- `CLAUDE.md`의 역할 분담 표를 실제 역할 배정으로 갱신하는 것 (이 시스템과 별개 논의)
- 종목명·티커 전달 여부의 자동(grep) 검사
