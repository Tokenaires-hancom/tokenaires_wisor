# 클린 코드 검수 — 파일 셋으로 다시 시작

작성일 2026-08-19

## 배경

`2026-08-18-precommit-clean-code-gate-design.md`가 설계한 검수 게이트를 **철거하고 처음부터 다시 만든다.**

기술적으로 고장난 곳이 있어서가 아니다. 하루 만에 파일 15개, 검사 스크립트 983줄이 쌓였고, 만든 사람(naemnaem99)이 **뭐가 뭔지, 실질적으로 의미가 있는지, 효율적으로 돌아가는지 판단할 수 없는 상태**가 됐다. 4명 다 비개발자인 팀에서 아무도 이해하지 못하는 검수 시스템은 검수를 하지 않는 것과 같다.

원칙 2("파급 범위 최소화 — 모듈을 작게, 서로 독립적으로")는 코드에만 적용되는 게 아니다. 검수 시스템 자체에 그 원칙을 적용해서, **작게 만들고 필요할 때 붙인다.**

### 다행인 사실

어제 만든 것은 `feat/clean-code-review-gate` 브랜치에만 있고 **develop에 하나도 올라가지 않았다.** 열린 PR도 없다. 그 15개는 "삭제"가 아니라 "합치지 않음"으로 끝난다.

실제로 지워야 하는 건 develop에 있는 더 오래된 것들이다.

## 클린 코드 5원칙

전통적 클린 코드(로버트 마틴류)는 "사람이 읽기 쉬운 코드"를 최우선으로 삼는다. 이 팀에는 두 가지 이유로 안 맞는다.

- **읽을 사람이 없다** — 4명 다 비개발자라 코드를 읽고 품질을 판단할 수 없다.
- **짜는 주체가 AI다** — "사람이 읽기 좋은가"보다 "AI가 다시 이 코드를 정확히 이해하고 고칠 수 있는가"가 더 중요하다.

그래서 "읽기 좋음"이 아니라 **"검증 가능함"**을 축으로 다섯 가지로 재정의한다.

1. **읽지 않고도 검증 가능해야 한다** — 통과/실패가 명확한 자동 테스트나 눈으로 확인 가능한 동작이 "코드가 맞다"는 증거를 대신한다.
2. **파급 범위 최소화** — 한 기능을 고치라고 AI에 시켰을 때 다른 곳이 깨지지 않도록 모듈을 작게, 서로 독립적으로 쪼갠다. 비개발자는 diff를 봐도 부작용을 못 알아챈다.
3. **중복 제로에 가깝게** — 같은 로직이 여러 곳에 있으면 AI가 한 곳만 고치고 나머지를 놓쳐서 눈에 안 보이는 불일치가 생긴다. 전통적 DRY보다 훨씬 엄격하게 지킨다.
4. **평범하고 뻔한 패턴 우선** — 똑똑한 트릭·추상화는 AI도 잘못 이해하고 재생성할 확률을 높인다. 예측 가능한 관용구가 "안전한" 코드다.
5. **의도는 자연어로 별도 기록** — 코드 내 주석보다 커밋 메시지·PR 본문에 "왜 이렇게 했는지"를 남겨야, 다음에 AI에게 다시 시킬 때 맥락을 넣어줄 수 있다.

## 목표

**5원칙을 두 층으로 나눠서 검수한다.**

- **기계가 판정하는 사실** — 테스트가 통과하나, 재무데이터가 새나. 틀릴 수 없으므로 **병합을 막는다.**
- **LLM이 내리는 판단** — 나머지 원칙. 틀릴 수 있고 이 팀은 반박할 수단이 없으므로 **절대 막지 않고 코멘트만 남긴다.**

두 층을 한 결과창에 섞지 않는다. 비개발자는 "막혔다(사실)"와 "이게 나을 것 같다(의견)"를 구별할 근거가 없고, 섞이면 둘 다 무시하게 된다.

## 목표가 아닌 것

- **LLM 판단에 강제성 부여.** 아래 "받아들인 한계" 참고.
- **자동 수정.** 검수 시스템이 검수 대상을 말없이 고치면 비개발자는 그 diff를 검토할 수 없다. 사람이 코멘트를 읽고 "3번 고쳐줘"라고 말하는 단계가 반드시 들어간다.
- **새 의존성.** 루트 `CLAUDE.md`의 "❌ 의존성 추가" 원칙 유지.
- 4명이 "좋은 코드를 알아보는 눈"을 기르는 것 — 이건 다른 문제다.

## 결정 사항

### 1. 전체 구조

```
CLAUDE.md 에 5원칙 (사전 지시 + 사후 검사 기준)
      │
      ▼
팀원이 개발 → git push 시도
      │
      ├─ 훅이 한 번 막고 "SKILL.md 를 읽고 수행하라"
      │
      ├─ 스킬: CLAUDE.md + 이번 diff 읽고 5원칙 항목별 코멘트   ← 판단, 안 막음
      │
      ├─ 사람이 읽고 "3번 고쳐줘" (또는 그냥 넘어감)
      │
      └─ push → PR
              │
              └─ check.yml: 테스트·빌드·타입체크·유출 grep      ← 사실, 막음
```

만들 파일은 **셋**이다.

| 파일 | 하는 일 | 층 | 분량 |
|---|---|---|---|
| `.claude/skills/clean-check/SKILL.md` | 5원칙 항목별 코멘트 | 판단 | 40줄쯤 |
| `.claude/hooks/pre-push-check.sh` | push 감지 → 스킬 수행 지시 | — | 40줄쯤 |
| `.github/workflows/check.yml` | 테스트 4줄 | 사실 | 30줄쯤 |

고칠 파일은 **둘**이다. 루트 `CLAUDE.md`(5원칙 섹션), `.claude/settings.json`(훅 등록).

이 외에 `.git/clean-check-state` 하나가 실행 중에 생긴다. gitignore 대상이고 커밋되지 않는다 — 위 "파일 셋"은 **저장소에 커밋되는 파일** 기준이고, 어제 "15개"도 같은 기준으로 센 숫자다.

**플러그인으로 만들지 않는다.** 저장소 `.claude/` 아래 두면 `git clone`으로 4명에게 자동으로 딸려간다. 각자 설치할 것이 없다 — 어제 시스템이 `/code-review`(개인 마켓플레이스 플러그인)에 의존해서 나머지 3명에게 도는지조차 확인 못 했던 문제가 여기서 사라진다.

### 2. 스킬 — `.claude/skills/clean-check/SKILL.md`

**하는 일**

1. `git diff <base>..HEAD` — 이번에 push될 변경 전체
2. 루트 `CLAUDE.md` + 변경된 디렉터리의 `CLAUDE.md` 읽기
3. 5원칙 항목별로 판정하고 코멘트 출력
4. `.git/clean-check-state`에 이번 diff 해시 기록 (훅이 재차단하지 않도록)

**출력 형식 — 고정**

원칙 5개를 순서·이름 그대로 항목으로 쓴다. 항목을 늘리지도 줄이지도 않는다.

```markdown
## 클린 코드 5원칙 검수

**1. 읽지 않고도 검증 가능** ⚠️
lib/masterMatch.ts 를 새로 만들었는데 대응하는 테스트가 없습니다.
→ 이 파일이 맞게 동작하는지 지금은 확인할 방법이 없습니다.

**2. 파급 범위 최소화** ✅
파일 6개, apps/web 한 영역 안에서만 바뀌었습니다.

**3. 중복 제로** ❌
MasterComparisonInteractive.tsx 88~120줄과
MasterDiagnosisQuiz.tsx 45~77줄이 거의 같습니다.
→ 나중에 한쪽만 고치면 두 화면이 서로 다르게 동작합니다.
(CLAUDE.md "클린 코드 원칙" — "같은 로직을 복붙하지 말고 함수로 뽑아 재사용")

**4. 평범한 패턴** ✅
이 저장소에서 이미 쓰던 방식대로 작성됐습니다.

**5. 의도 기록** ⚠️
최근 커밋 메시지에 "무엇을 바꿨는지"는 있는데 "왜"가 없습니다.
→ 다음에 AI에게 이 부분을 다시 시킬 때 넣어줄 맥락이 없습니다.
```

**지키는 규칙 넷**

- 항목마다 ✅/⚠️/❌ 하나. 그 아래는 **왜 문제인지 한 줄** — "무엇이 잘못됐다"가 아니라 "그래서 나중에 뭐가 터진다".
- **근거가 CLAUDE.md에 있는 지적만 ❌.** 문서에 근거가 없고 일반론이면 ⚠️로 낮추고, 어느 문장을 근거로 삼았는지 인용한다. 비개발자는 애매한 지적을 판단할 수 없어서 무조건 "고쳐줘"라고 하게 되고, 필요 없는 수정이 또 파급을 만든다. (`/code-review`의 확신도 필터에서 가져온 규칙이다.)
- **문제가 없어도 5개 항목을 전부 출력한다.** 침묵은 "깨끗함"과 "안 돌았음"이 구별되지 않는다.
- **고치지 않는다.** 지적만 하고 멈춘다.

**스킬은 테스트를 돌리지 않는다.** diff를 보고 "테스트가 **있나**"만 판단한다. "**통과하나**"는 `check.yml`이 본다. 스킬이 테스트까지 돌리면 push마다 몇 분씩 걸려서 아무도 안 쓰게 된다. 원칙 1은 이 둘이 합쳐져야 완성된다.

### 3. 훅 — `.claude/hooks/pre-push-check.sh`

`PreToolUse` 훅으로 `git push`를 감지한다. 동작은 셋뿐이다.

1. 이번에 나갈 diff를 구한다 (upstream이 있으면 `@{upstream}..HEAD`, 없으면 `origin/develop..HEAD`)
2. 그 diff 해시가 `.git/clean-check-state`에 기록된 것과 같으면 그냥 통과
3. 다르면 `permissionDecision: deny` + 아래 문구

훅은 스킬을 직접 호출할 수 없다. `deny` 이유 문구가 Claude에게 전달되고, Claude가 그걸 읽고 실행하는 구조다.

**이유 문구는 스킬 이름이 아니라 파일 경로를 준다.**

```
"push 전 클린 코드 검수가 아직 안 됐습니다.
 .claude/skills/clean-check/SKILL.md 를 읽고 그대로 수행한 뒤 다시 push하세요."
```

`/clean-check`처럼 이름으로 부르면 **프로젝트 로컬 스킬이 그 팀원 세션에 등록돼 있어야** 한다. clone만 한 상태에서 인식되는지 검증되지 않았고, 안 되면 `/code-review` 미설치 문제를 이름만 바꿔 재현하게 된다. 파일 경로를 주면 그냥 읽어서 수행하므로 등록 여부와 무관하다. 스킬로도 등록돼서 `/clean-check`로 불리면 그건 덤이다.

**오버라이드 경로를 만들지 않는다.** 검수 결과가 push를 막지 않으므로(지적만 하고 진행) 강행할 이유가 없다. 어제 시스템은 하드블록이 있었기 때문에 오버라이드 → 흔적 남기기 → 게이트키퍼 승인 확인이 줄줄이 따라붙어 파일이 불어났다.

### 4. CI — `.github/workflows/check.yml`

PR을 열거나 새 커밋을 push하면 돈다. **이것만 병합을 막는다.**

```
data-pipeline && pytest -q
apps/web && npm run build
apps/web && npx tsc --noEmit
apps/web && .next/static/ 에 "evEbitMedian5y" 가 있으면 실패
```

명령 네 개고 읽으면 그대로 이해된다. **py 파일이 0개다.**

(마지막 줄을 `grep ... && exit 1 || true` 한 줄로 쓰면 `|| true`가 `exit 1`을 삼켜서 **절대 실패하지 않는다.** `if`문으로 쓴다 — 실제 파일 참고.)

- 앞의 셋은 원칙 1의 "통과/실패가 명확한 증거" 그 자체다. 어제까지는 pre-commit 훅이 돌렸는데 그 훅을 없애므로, **여기 없으면 아무도 안 돌린다.**
- 마지막 줄은 클라이언트 번들에 재무데이터가 실렸는지 본다. 되돌릴 수 없는 유출이라 유일하게 예외로 남기는 검사다. `boundary_check.py`(118줄)를 대체하며, **소스에서 import를 찾는 것보다 빌드 결과물을 grep하는 쪽이 확실하다** — 중간 모듈을 거친 간접 유출까지 잡힌다. 어차피 `npm run build`를 돌려야 grep 대상(`.next/static/`)이 생기므로 스텝이 늘지도 않는다.

**LLM을 부르지 않는다.** GitHub 시크릿에 4명 토큰을 등록해 쓰는 `claude.yml` 같은 복잡도가 여기엔 없다. 판단은 전부 로컬 스킬이 한다.

**`pr-review.yml`의 나머지 검사를 안 가져오는 이유**

| 안 가져오는 검사 | 이유 |
|---|---|
| develop 병합 가능 여부 | GitHub이 PR 화면에 이미 표시한다 |
| PR 제목·본문 형식 | 스킬 5번 항목이 본다 |
| 문자 그대로의 중복 | 스킬 3번 항목이 본다 |
| 경계 검사 | 위 grep이 더 확실하게 대체한다 |
| 오버라이드 게이트키퍼 승인 | 새 설계엔 오버라이드가 없다 |

### 5. `CLAUDE.md` 5원칙 섹션

지금 "클린 코드 원칙 (AI 검수 기준)" 섹션은 4개뿐이고(원칙 1 없음) 문장이 **검수 기준**으로 쓰여 있다. 5개로 채우고 **코드를 짜는 AI에게 주는 지시문**으로 바꾼다.

```
❌ "파급범위를 최소화합니다"
✅ "한 번에 한 가지만 고친다. 다른 영역을 건드려야 하면 먼저 말한다."

❌ "중복 없이 재사용합니다"
✅ "새 함수를 짜기 전에 같은 일을 하는 게 이미 있는지 먼저 찾는다."
```

이 한 파일이 **사전(코드 짤 때)과 사후(검수할 때) 양쪽의 기준**이 된다. 세션 시작 시 자동으로 컨텍스트에 들어가고, 스킬도 이걸 읽는다.

원칙 2·4는 코드를 다 쓴 뒤에 잡아봐야 이미 늦다(다시 짜야 한다). 그래서 사전이 본체고 스킬은 안전망이다. **작업을 작게 시키는 것**이 원칙 2의 실질 수단이고, 이건 도구로 해결되지 않는다.

### 6. `/code-review`, `/simplify` 는 시스템에 넣지 않는다

권장하되 강제하지 않는다. `CLAUDE.md`에 한 줄만 남긴다.

> push 전에 `/code-review`를 돌리면 지적이 덜 나옵니다. 필수는 아닙니다.

확인한 사실:

- `/code-review`는 CLAUDE.md를 **실제로 읽는다.** 전담 에이전트가 준수 감사를 하고, 원문을 인용하고, 0~100 확신도로 오탐을 거른다. 어제 spec의 전제는 맞았다.
- 다만 품질 지적을 기본적으로 버린다 — "General code quality issues ... **unless explicitly required in CLAUDE.md**". 5원칙이 CLAUDE.md에 적혀 있어야만 본다.
- 80점 미만을 전부 필터하고, 남는 게 없으면 **코멘트를 아예 안 남긴다.** 우리는 5항목이 매번 찍히길 원하므로 형식이 안 맞는다.
- 출력이 findings 목록(파일:줄 + 확신도)이라 개발자용이다.
- `/simplify`는 재사용·단순화·효율·추상화 수준을 보고 **직접 고친다.** 앞의 세 개는 `/code-review`와 겹치고, "고친다"는 이 팀에 단점이다. 따로 돌릴 이유가 없다.

## 받아들인 한계

**LLM 판단 층(스킬)은 우회할 수 있다.** 셋 다 실재한다.

- 터미널에서 `git push` — Claude Code 훅은 안 걸린다
- `git push --no-verify`
- Claude Code를 안 쓰고 작업

강제하려면 이런 게 따라온다 — git 네이티브 훅 + 4명 각자 `core.hooksPath` 설정, `--no-verify` 감지, 오버라이드 경로, 흔적 기록, 게이트키퍼 승인 확인. **어제 15개 파일이 된 경로가 정확히 이것이다.**

지금은 우회 가능한 채로 둔다. **이해 못 하는 완벽한 시스템보다 이해하는 새는 시스템이 낫다.**

다만 **사실 층(`check.yml`)은 우회할 수 없다.** 어떻게 push하든 PR을 열면 무조건 돌고, 실패하면 병합이 막힌다. 되돌릴 수 없는 사고(테스트 깨짐, 재무데이터 유출)는 이쪽이 잡는다.

우회가 실제 문제로 드러나면 → 아래 "나중에" 참고.

### branch protection

develop 현황 (2026-08-19 확인):

```
required_status_checks: ["auto-checks"]   ← pr-review.yml 의 job 이름
strict: true
required_approving_review_count: 1
require_code_owner_reviews: true
enforce_admins: false
```

**교체하되, 그 사이에 잠깐 비는 구간이 있고 순서를 지켜야 한다.**

`pr-review.yml`을 지우는 PR은 **그 브랜치에 워크플로 파일이 없으므로 `auto-checks`가 아예 안 뜬다.** 필수 검사가 영원히 pending 상태로 남아 **그 PR 자체가 병합 불가**가 된다. 반대로 `check.yml`은 아직 develop에 없어서 미리 등록할 수도 없다(등록해도 같은 이유로 안 뜬다).

그래서 순서는 이렇다.

```
1. branch protection 에서 auto-checks 를 뺀다   ← 필수 검사가 잠깐 0개가 된다
2. PR 병합
3. check.yml 의 job 이름을 필수 검사로 등록
```

1~3 사이에 다른 PR을 병합하지 않으면 빈 구간의 위험은 없다. 승인 1명·코드오너 리뷰는 이 구간에도 그대로 살아 있다.

승인 1명·코드오너 리뷰는 그대로 둔다 — 검수 시스템이 아니라 협업 규칙이다.

**주의**: 이 PR은 `.claude/**`와 `CLAUDE.md`를 건드리므로 CODEOWNERS상 naemnaem99 승인이 필요한데, **본인 PR은 본인이 승인할 수 없다.** 팀원 1명의 승인이 필요하다(naemnaem99는 admin이고 `enforce_admins: false`라 필요시 우회 가능).

- 깨끗한 변경으로 push해서 5개 항목이 전부 출력되는지 (침묵하지 않는지)
- 일부러 테스트를 깨뜨린 PR에서 `check.yml`이 실패하고 병합 버튼이 잠기는지

## 나중에

지금 넣지 않는다. 실제로 필요해진 게 보이면 그때 붙인다. **하나씩.**

| 언제 | 무엇을 |
|---|---|
| 코멘트가 중복을 자꾸 놓치면 | `duplicate_check.py` 되살리기 (브랜치에 305줄 그대로 있음) |
| 테스트 없는 파일이 자꾸 통과하면 | 테스트 동반 여부 검사를 `check.yml`에 |
| 우회가 실제 문제가 되면 | 스킬 프롬프트를 그대로 GitHub Actions로 옮기기 |
| 실패 로그를 아무도 못 읽으면 | `check.yml` 결과를 사람 말로 번역해 PR 코멘트로 |

**스킬 프롬프트는 버리는 작업이 아니다.** 5원칙 항목 형식, 확신도 규칙, 문장 톤이 이 시스템의 알맹이고 실행 장소는 껍데기다. CI로 옮길 때 그대로 복사된다.
