# 챗봇에 비점수 대가 세 명을 더한다 — 설계

날짜: 2026-08-20
브랜치: feat/persona-chat-master-selector

## 무엇을

챗봇 페르소나가 넷(버핏·그레이엄·린치·그린블랫)뿐이다. 전부 `scores.json`의 채점
스타일과 1:1로 묶여 있고, 대화 앵커가 `<지표>` + `<기준판정>` 블록이다.

사이트 대가는 일곱이다. `apps/web/content/masters.ts`에서 피셔·막스·소로스는
`evaluation: "checklist"`로 표시돼 있고 `scores.json`에 없다. 판정할 것이 없으니
같은 답변 틀을 쓸 수 없다.

이 셋을 챗봇에 더한다.

## 왜

배우기 화면에서는 일곱 명을 만나는데 챗봇에서는 넷만 나온다. 사이트가 가르치는
철학의 절반이 대화로 이어지지 않는다. 그리고 세 사람이야말로 숫자가 아니라
"무엇을 확인해야 하는가"를 다루는 관점이라, 이 제품의 방향과 정확히 맞는다.

## 결정

### 앵커 — 종목 이름만, 지표는 뺀다

`ticker`는 그대로 받되 앵커 블록에서 숫자를 뺀다. `<회사>` 블록 하나다.
API 계약(`ticker` 필수)이 그대로라 프론트 변경이 작고, 숫자로 판정하는 사고가
구조적으로 불가능해진다.

### 답변 틀 — 확인 질문 + 어디서 확인하나

항목마다 `묻는 것 / 어디서 확인하나 / 어떤 답이면 논거가 깨지나`. 답을 사용자가
가져오게 만들어, 모델이 회사를 대신 평가할 자리를 없앤다.

### 규칙 분할

`COMMON_RULES`는 숫자 규칙이 절반이라 지표 없는 대가에게 그대로 걸 수 없다.
양쪽이 글자까지 같은 조각(`[절대 하지 않는 것]`, `[형식]` 앞머리, 면책 문구)만
상수로 뽑아 공유하고, 나머지는 각자 쓴다. 안전 규칙이 두 벌로 갈라지지 않게
하는 것이 분할의 목적이다.

`COMMON_RULES`의 최종 문자열은 **바이트 하나도 바뀌지 않아야 한다.** 기존 네
페르소나 × 플래그 4조합 = 16개 프롬프트 해시로 검증한다.

### 사전지식 금지 규칙을 대체한다

지금 "오직 `<지표>` 블록의 숫자만으로 설명한다"가 모델이 회사에 대해 아는 척하는
것을 막고 있다. 지표를 빼면 이 문장이 빈 규칙이 되고 남는 재료는 사전학습 지식뿐이다.
숫자가 사라지면 환각 위험은 내려가는 게 아니라 올라간다.

그래서 자리를 비우지 않고 적극적으로 대체한다: **답변은 물을 것과 어디서 확인하는지만
담는다. 이 회사가 어떠하다는 서술을 하지 않는다.**

### 본문 출처

`masters.ts`의 `principles` / `likes` / `failsWhen`을 옮긴다. 커리큘럼이 원문·정리·창작을
구분해 둔 이유가 있으므로, 그 사람이 쓴 것처럼 읽히는 항목을 새로 지어내지 않는다.

## 손대는 곳

| 파일 | 변경 |
|---|---|
| `persona_explain/personas.py` | `kind` 속성, 규칙 분할, 페르소나 본문 3개 |
| `persona_explain/explain.py` | `format_company_block`, `explain_all`은 score만 |
| `persona_explain/chat.py` | 판정 없는 앵커, `switch_persona`가 kind를 먼저 본다 |
| `persona_explain/server.py` | `_supported_personas`가 `PERSONAS` 순서, `evaluation` 필드 |
| `persona_explain/챗봇_API계약.md` | 페르소나 id 셋 추가, `judgement: null`, `evaluation` |
| `apps/web/components/PersonaChatFab.tsx` | `FALLBACK_PERSONAS`에 셋 추가 |

### 클릭 한 번에 깨지는 지점

`chat.py`의 `switch_persona`는 `judgement is None and self.company is not None`
분기가 먼저 걸려 `data.judgement(ticker, "fisher")`를 부른다. `UnknownStyle`이 난다.
대상 페르소나의 `kind`를 그 분기 **앞에서** 봐야 한다. 서버의 관점 교체가 전부
이 경로를 지난다.

### 페르소나 순서

`_supported_personas`가 `data.style_ids()` 대신 `PERSONAS`를 돌면 기존 넷의 순서도
바뀐다. `masters.ts` 순서(버핏·그레이엄·린치·막스·피셔·그린블랫·소로스)로 고정해
사이트와 맞춘다.

## 검증

1. 프롬프트 해시 16개 바이트 동일 — 기존 넷 무변경 증명
2. `pytest -q` — 78 passed 유지
3. 새 테스트: 앵커에 `<지표>` 없음 · 사전지식 금지 규칙 살아있음 · 페르소나 교체 왕복
4. `npm run build`

## 이번에 하지 않는 것

- `test_scores_source.py::test_real_file_has_expected_metric_keys`는 이미 깨져 있다.
  `scores.json`에 `magicFormulaRoc`가 생겼는데 변환표에 없다. 이번 작업과 무관해 남긴다.
- 체크리스트 대가의 채점·스크리너 화면. 이 셋은 점수를 내지 않는다.

## 개정 — 2026-08-20, 답변이 뻣뻣하고 종목마다 같다

실제 답변을 읽어 보니 세 가지가 걸렸다. 종목이 달라도 답이 같고, 말투가 딱딱하고,
알맹이가 얇다. 제약 셋을 푼다.

### 대가가 1인칭으로 말한다 — 일곱 명 전부

`- 대가를 3인칭으로 소개한다… 1인칭으로 말하지 않는다` 를 뒤집는다. 이 줄은
점수 대가와 확인 대가가 함께 쓰는 `_FORMAT_HEAD`에 있어 일곱 명이 같이 바뀐다.

근거를 찾아봤다. `2026-08-06-learn-curriculum-design.md`의 3인칭 규칙은 "지금 파세요"
같은 명령형을 막는 것이지 대가가 자기 목소리로 말하는 것을 막는 규칙이 아니다.
챗봇 쪽 1인칭 금지는 최초 커밋부터 근거 기록 없이 있었다.

**남는 위험:** 1인칭이 되면 모델이 의견을 내고 싶어 한다. "나는 이 회사가 마음에
드네"는 사실상 권유다. 안전 필터(`safety.py`)는 키워드 기반이라 이런 문장을 잡지
못한다. 막는 것은 두 가지다 — 회사에 대한 서술 금지 규칙(그대로 둔다), 그리고
형식 규칙에 넣은 못 `[절대 하지 않는 것]은 1인칭이어도 그대로다`.

### 확인 항목을 본문 목록으로 가두지 않는다

`- 확인 항목은 … 있는 것만 쓴다. 새로 만들지 않는다` 를 뺀다. 본문 목록은 출발점이
되고, 물어본 것과 업종에 맞춰 항목을 다듬거나 새로 만들 수 있다.

항목 수(4~5개)와 마무리 두 문장 제한도 함께 뺀다. 이 둘이 "알맹이가 없다"의 직접
원인이었다.

### 업종은 근거로 써도 된다

"종목이 달라도 답이 같다"는 지금 구조로는 못 고친다. 앵커에 들어가는 종목별 정보가
이름과 업종뿐인데 회사에 대해 아무 말도 못 하게 돼 있어 쓸 재료가 없기 때문이다.

그래서 업종만 연다. **업종 일반론으로 확인 질문을 다듬는 것은 허용하고, 이 회사에
대한 주장은 계속 막는다.** 경계가 흐려지지 않게 프롬프트에 예시를 나란히 둔다.

```
쓴다   — "장비를 파는 업종은 대개 소모품 매출이 뒤따르네. 그 비중을 확인해 보게."
안 쓴다 — "이 회사는 소모품 매출 비중이 높네."
```

### 손대지 않은 것

- 회사에 대한 서술 금지 — 1인칭 전환의 안전판이라 오히려 더 중요해졌다
- 숫자 창작 금지, 매수·매도·목표가 금지, 면책 문구
- 점수 대가의 지표 해설 형식과 임계값

### 검증

지난번과 달리 **기존 네 명의 프롬프트도 의도적으로 바뀐다.** 해시 동일성 대신,
버핏 프롬프트를 줄 단위로 비교해 인칭 관련 문장 외에는 바뀐 곳이 없음을 확인한다.

## 개정 2 — 2026-08-20, 회사 서술 금지를 출처 표시로 바꾼다

`checklist` 관점의 회사 서술 금지를 뺀다. 회사 얘기를 하게 한다.

### 대신 모든 주장에 출처를 붙인다

"출처를 밝히게 하라"를 그대로 구현하면 역효과가 난다. 모델은 진짜 출처를 확인할 수
없어서 열어 두면 "2024년 3분기 보고서에 따르면" 같은 인용을 지어낸다. 지어낸 인용은
확인된 것처럼 보여 아무 표시가 없는 것보다 위험하다.

그래서 출처를 **밝히게** 하는 대신 **세 종류로 가둔다.** 커리큘럼이 원문·정리·창작으로
근거를 가르는 것과 같은 장치다.

| 표시 | 뜻 |
|---|---|
| `[주어진 것]` | `<회사>` 블록에 실제로 적힌 것. 종목명·티커·업종뿐 |
| `[업종 통례]` | 그 업종이 대체로 어떤 구조인지에 대한 일반론. 이 회사에 대한 주장이 아님 |
| `[내 기억]` | 학습 자료에서 본 기억. 최신이 아닐 수 있고 틀릴 수 있음 |

`[내 기억]`으로 말할 때는 확인되지 않은 기억이라는 사실과 사용자가 직접 확인할 곳을
함께 준다. 후속 답변에서도 표시를 유지한다.

### 수치만 남긴 제약

이 회사의 구체적 수치는 `[내 기억]`으로도 말하지 않는다. 날짜와 출처가 없는 숫자는
화면에 기준일과 함께 떠 있는 숫자와 어긋난다. 루트 CLAUDE.md의 "현재라고 쓰지 않고
날짜를 쓴다"와 직접 충돌하는 유일한 항목이라 이것만 남겼다. 수치 대신 방향과 성격을
말하고, 숫자는 확인할 곳을 알려 준다.

### 점수 대가는 그대로다

`score` 관점의 사전지식 금지는 손대지 않았다. 그쪽은 `scores.json`에서 꺼낸 값이
앵커에 실려 있고, 모델이 기억 속 숫자를 섞으면 화면의 기준 막대와 다른 숫자를
말하게 된다. 앵커 구조 전체가 그것을 막으려고 있다.

### 남는 위험

`[내 기억]` 표시가 붙어 있어도 내용은 여전히 틀릴 수 있다. `safety.py`는 키워드
기반이라 틀린 사실을 잡지 못한다. 이 변경으로 이 기능의 사실 정확도는 보장 대상에서
빠지고, 사용자가 확인하는 것을 전제로 한다.
